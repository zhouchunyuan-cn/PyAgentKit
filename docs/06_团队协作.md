# 第 6 章：团队协作

> 目标：理解多个 Agent 如何组成"团队"，按流程协作完成复杂任务。

## 6.1 这一章解决什么问题

第 5 章的 Router 让 Agent 间能互发消息，但那是"消息路由"——谁发给谁靠 Agent 自己在代码里 `send`。如果要换一种协作流程，就得改 Agent 的代码。

**Team（团队）** 是更高层的抽象：把"成员有哪些"和"按什么流程协作"分开。成员就是普通 Agent，流程由 **Process** 决定。换个 Process 就换种协作方式，无需改 Agent。

## 6.2 Team 与 multi-agent 的区别

| | multi-agent（Router） | Team（Process） |
|---|---|---|
| 关注点 | 谁发给谁（消息路由） | 按什么顺序、谁做什么（流程编排） |
| 数据传递 | 各自独立的 memory | **SharedContext 共享黑板** |
| 流程 | 写死在 Agent 的 send 里 | 由 Process 声明，可切换 |
| 适用 | 松散的、对等的 Agent 通信 | 有共同目标、有分工的团队 |

## 6.3 核心组件

### SharedContext——团队共享黑板

团队成员通过它共享中间产物，而非各自独立的 memory：

```python
class SharedContext:
    task: str                          # 团队共同目标
    outputs: Dict[agent_id, str]       # 各成员的最新产出（get_output 取最新）
    output_log: List[Dict]             # 完整产出日志（同成员多次产出都保留）
    intermediate: Dict[str, Any]       # 中间产物（如 Leader 的规划）
    history: List[Dict]                # 执行步骤记录
```

关键方法 `get_all_outputs()`：按时间顺序拼接**所有**产出（同一成员多次执行时每次都出现），作为下一个成员的输入上下文。`to_dict()` / `from_dict()` 负责黑板的序列化与还原——这是断点续跑的基础（见 6.6）。

### Process——流程策略

抽象基类，定义"团队成员怎么协作"：

```python
class Process(ABC):
    def execute(self, task, members, leader=None, stream_callback=None,
                checkpoint_state=None, save_checkpoint=None, step_limit=None) -> str | None:
        """执行团队任务；step_limit 触发暂停时返回 None（进度已落盘）"""
```

两种内置实现：SequentialProcess（顺序接力）和 HierarchicalProcess（Leader 编排）。

### Team——团队

```python
class Team:
    def __init__(self, name, members, process, leader=None,
                 checkpoint_store=None)             # checkpoint_store 开启断点续跑
    def run(self, task_description, stream_callback=None, run_id=None) -> str
    def run_resumable(self, task_description, run_id, step_limit=None) -> RunOutcome
```

`stream_callback` 传入后，最终结果会**流式产出**（Sequential 传给最后一个成员，Hierarchical 传给 Leader 汇总步骤）。

## 6.4 SequentialProcess——顺序接力

最直观的流程：成员按声明顺序执行，前者的产出作为后者的上下文。

```
任务："写一篇科普文章"
  │
  ├─ 成员1（研究员）: 收到任务 → 思考 → 产出"研究要点"
  │     ↓ 产出存入 SharedContext
  ├─ 成员2（作家）: 收到"任务 + 研究员的要点" → 思考 → 产出"文章初稿"
  │     ↓ 产出存入 SharedContext
  └─ 成员3（审核员）: 收到"任务 + 前两人产出" → 思考 → 产出"终稿"
        ↓
     最终结果 = 成员3的产出
```

每个成员的输入由 `_build_input` 组装：
- 第一个成员：只收到原始任务
- 后续成员：收到"团队任务 + 此前所有人的累计产出"

```python
from core import Team, SequentialProcess

team = Team(
    name="内容组",
    members=[researcher, writer, reviewer],
    process=SequentialProcess(),
)
result = team.run("写一篇关于量子计算的科普文章")
```

**适用**：固定的确定性流水线（研究→写作→审核）。

## 6.5 HierarchicalProcess——Leader 自动编排 ⭐

这是 Team 模块的精华。Leader 用 LLM **动态分析任务、自动拆解、按能力分配成员、最后汇总**。

### 三阶段流程

```
任务："完成一份 AI 行业分析"
  │
  ├─ 阶段1: 规划（Leader）
  │    Leader 收到任务 + 成员能力清单，输出 JSON 子任务规划：
  │    [{"subtask": "调研 AI 行业数据", "capability": "search"},
  │     {"subtask": "分析市场趋势", "capability": "analysis"},
  │     {"subtask": "撰写报告", "capability": "write"}]
  │
  ├─ 阶段2: 执行（按能力匹配成员）
  │    子任务1 → 找具备 search 能力的成员 → think → 产出存入 context
  │    子任务2 → 找具备 analysis 能力的成员 → think（带着子任务1的产出）→ 产出
  │    子任务3 → 找具备 write 能力的成员 → think（带着全部产出）→ 产出
  │
  └─ 阶段3: 汇总（Leader）
       Leader 收到"任务 + 所有成员产出"，think 出最终结果
```

### Leader 的规划 prompt（结构化输出）

规划走 `response_format={"type": "json_object"}`——模型被约束为只能输出合法 JSON，可靠性远高于"自由文本 + 正则抠取"：

```
你是项目经理。任务：{task}
成员及能力：{members}
请拆解为子任务，每个指定所需能力。只输出 JSON 对象：
{"subtasks": [{"subtask": "...", "capability": "..."}]}
```

`_parse_plan` 多级容错：优先整体 JSON 解析（json_object 模式的正常产物）→ 从自由文本中截取 JSON 对象/数组（不支持该参数的客户端的兜底）→ 校验字段过滤无效项。全部失败时回退为"每个成员处理一个通用子任务"，保证健壮性。

### 能力匹配

`_find_member_by_capability(members, capability)` 找到第一个声明了该能力的成员。这正是第 2 章讲的 `capabilities` 的用武之地——**协作系统按能力选人，而非靠名字硬编码**。

```python
from core import Team, HierarchicalProcess

team = Team(
    name="项目组",
    members=[researcher, analyst, writer],
    process=HierarchicalProcess(max_subtasks=4),
    leader=manager,   # manager 声明了 capabilities=["plan"]
)
result = team.run("完成一份 AI 行业分析")
```

### 流式输出

团队任务通常耗时较长。传入 `stream_callback` 可让最终结果实时输出，而非干等：

```python
chunks = []
team.run("写一份报告", stream_callback=lambda s: chunks.append(s))
# Sequential：最后一个成员（如作家）的输出实时回调
# Hierarchical：Leader 汇总步骤的输出实时回调
```

## 6.6 并行执行（fan-out）

依赖前序产出的流水线必须串行，但很多任务的子步骤是**相互独立**的——三个成员各查各的，串行就是白白浪费时间。`HierarchicalProcess(parallel_subtasks=True)` 开启子任务并行：

```python
team = Team(
    name="并行组",
    members=[researcher, analyst, writer],
    process=HierarchicalProcess(parallel_subtasks=True),
    leader=manager,
)
```

并行策略是**按执行成员分组：组间并行、组内串行**——两个子任务命中同一个成员时，该成员在自己的组里顺序执行，会话状态不会被并发写坏；不同成员之间互不阻塞。同一时刻 ReAct 循环内的多个工具调用也是并发的（第 2 章），所以"成员并行 + 工具并行"可以叠加。

注意：并行模式下各子任务拿不到彼此的产出（同时进行），任务间有依赖时用默认的顺序模式。YAML 一行开启：`team: { process: hierarchical, parallel: true }`。

## 6.7 断点续跑（Checkpoint）⭐

团队任务动辄几十秒、几十次 LLM 调用。中途崩溃，全部产出丢失；想先看中间结果再决定继续，也做不到。检查点（`core/checkpoint.py`）解决这两个问题：

```python
from core import FileCheckpointStore

team = Team(name="内容组", members=[researcher, writer, reviewer],
            process=SequentialProcess(),
            checkpoint_store=FileCheckpointStore(".checkpoints"))

# 崩溃恢复：同 run_id 重跑，从断点继续——已执行的成员不再重跑（LLM 不重复付费）
result = team.run("写一份行业分析", run_id="report-101")

# 分步执行：跑 1 步暂停，人工检查后续跑
outcome = team.run_resumable("写一份行业分析", run_id="report-101", step_limit=1)
if not outcome.completed:
    ...  # 审查中间产出
    outcome = team.run_resumable("写一份行业分析", run_id="report-101")
print(outcome.result, outcome.steps_done)
```

机制要点：

- **每步原子落盘**：每完成一个成员/子任务，把流程状态 + 整个 SharedContext 黑板原子写入 JSON（先序列化再临时文件 + rename，坏值不会破坏旧检查点）
- **Hierarchical 续跑复用规划**：断点里存着 Leader 上次的子任务规划，续跑直接复用——不再花一次 LLM 调用重新规划
- **完成态幂等**：已完成的 run 同 run_id 再执行，直接返回缓存结果，零 LLM 调用
- **任务变化自动作废**：同 run_id 但任务描述不同，旧检查点被忽略并重新开始

## 6.8 两种流程怎么选

| | Sequential | Hierarchical |
|---|---|---|
| 流程 | 固定顺序 | Leader 动态决定 |
| 确定性 | 高（每次一样） | 低（Leader 可能拆出不同子任务） |
| 智能 | 低（机械接力） | 高（理解任务后规划） |
| 成本 | 低（N 次 think） | 高（N + 规划 + 汇总次 think） |
| 适用 | 已知流水线 | 不确定该谁做什么的复杂任务 |

## 6.9 用 YAML 配置团队（无需写代码）

```yaml
# configs/team_example.yaml
llm:
  model: glm-4-flash
agents:
  - id: leader
    capabilities: [plan]
  - id: researcher
    capabilities: [search]
    tools: [web_search]
  - id: writer
    capabilities: [write]
team:
  name: 内容组
  process: hierarchical
  leader: leader
  members: [researcher, writer]
  # parallel: true        # 可选：子任务按成员分组并行（见 6.6）
  # max_subtasks: 4       # 可选：Leader 最多拆几个子任务
```

```bash
pyagentkit run configs/team_example.yaml
# 进入团队交互模式，输入任务即触发 Leader 编排
```

详见第 8 章。

## 6.10 与其他模块的关系

- 成员就是普通 Agent，复用 `think()`（第 2 章）
- 能力匹配依赖 `Agent.capabilities`（第 2 章）
- `SharedContext` 替代了 Router 场景下各自独立的 memory（第 5 章）
