# 实战：构建智能研究报告生成器（0.4 毕业项目）

> 本篇是一个**端到端的项目实战**。我们将从零构建一个完整的应用：输入一个主题，
> 团队自动调研、分析、撰写，产出一份结构化研究报告。
>
> 通过这个项目，你会把前 8 章学到的能力**全部**串起来用一遍：
> **ReAct 推理 + 工具调用 + 团队协作 + 流式事件 + 执行追踪 + 断点续跑 + 并行优化**。

---

## 项目目标

做一个**智能研究报告生成器**：

```
输入："人工智能在医疗领域的应用"
                │
                ▼
   ┌─────────────────────────────┐
   │   团队（Leader 自动编排）      │
   │                             │
   │  Leader: 拆解任务（结构化输出） │
   │    ├─ 研究员: 联网搜索资料     │
   │    ├─ 分析师: 解读关键趋势     │
   │    └─ 作家: 撰写结构化报告     │
   │  Leader: 汇总终稿            │
   └─────────────────────────────┘
                │
                ▼
输出：一份带标题、要点、结论的研究报告
（全程流式可见；中断可续跑，已跑步骤不重复计费）
```

## 你将学到

- 如何设计多 Agent 团队的角色分工（capabilities 驱动 Leader 分配）
- 如何用 `web_search` 工具让 Agent 联网获取真实信息
- 如何用**流式事件**实时观察思考与工具调用（第 2/7 章）
- 如何用 **Tracer** 事后复盘协作过程（谁做了什么、耗时、token）
- 如何用**断点续跑**让长任务崩溃可恢复、可分段执行（第 6 章）
- 如何用**并行子任务**压缩耗时（第 6 章）
- 如何用 YAML 配置让一切可复现、可调整（第 8 章）

## 第 1 步：理解需求与角色设计

一份好的研究报告需要四个角色协作：

| 角色 | 能力 (capabilities) | 职责 | 工具 |
|------|---------------------|------|------|
| **项目经理** | `plan` | 拆解任务、分配、汇总 | 无（纯推理） |
| **研究员** | `search` | 联网搜集资料 | `web_search` |
| **分析师** | `analysis` | 解读资料、提炼趋势 | 无 |
| **作家** | `write` | 整理成结构化报告 | 无 |

为什么这样分？因为 Hierarchical 流程的 Leader 会按 `capability` 匹配成员——我们让每个角色声明不同的能力，Leader 就能把"搜索"子任务分给研究员、"分析"分给分析师，各司其职。

## 第 2 步：用 YAML 声明团队（声明式）

创建配置文件 `configs/report_generator.yaml`：

```yaml
# 智能研究报告生成器配置
llm:
  model: glm-4-flash

agents:
  # 项目经理：负责拆解任务和汇总
  - id: leader
    name: 项目经理
    system_prompt: |
      你是一个经验丰富的项目经理。
      收到研究任务后，你会把它拆解为若干子任务，每个子任务指定所需的能力。
      最后你会汇总所有成员的产出，形成连贯的最终报告。
    capabilities: [plan]

  # 研究员：联网搜集资料
  - id: researcher
    name: 研究员
    system_prompt: |
      你是专业研究员。收到调研任务后，使用 web_search 工具搜索真实信息，
      然后整理成要点。务必基于搜索到的真实内容，不要编造。
    capabilities: [search]
    tools: [web_search]

  # 分析师：解读资料
  - id: analyst
    name: 分析师
    system_prompt: |
      你是数据与行业分析师。基于研究员提供的资料，
      提炼关键趋势、机会与挑战，给出有洞察力的分析。
    capabilities: [analysis]

  # 作家：撰写报告
  - id: writer
    name: 报告撰写员
    system_prompt: |
      你是专业报告撰写员。把团队的调研和分析整理成结构清晰的报告，
      包含：标题、背景、核心发现（分点）、结论与展望。
    capabilities: [write]

# 团队：Leader 自动编排
team:
  name: 研究报告组
  process: hierarchical
  leader: leader
  members: [researcher, analyst, writer]
  max_subtasks: 4
  # parallel: true      # 进阶：子任务相互独立时可开启并行（见第 7 步）

session:
  agent: leader
```

> **关键点**：
> - `process: hierarchical` 让 Leader 用 LLM 智能分配，而非机械接力
> - Leader 的规划走 `response_format` JSON 模式，输出是受约束的合法 JSON（第 6 章）
> - 研究员挂了 `web_search` 工具，其他角色纯推理；工具参数有 schema 校验兜底（第 3 章）
> - `max_subtasks: 4` 限制 Leader 最多拆 4 个子任务，控制成本

## 第 3 步：用 CLI 跑起来（实时流式）

```bash
pyagentkit run configs/report_generator.yaml
```

进入团队交互模式后，输入一个研究主题：

```
task> 人工智能在医疗领域的应用现状与前景
```

CLI 会实时显示执行过程——助手文本逐字流出、推理模型的思考过程以暗色显示、每次工具调用有一行提示。等几十秒，报告输出。

## 第 4 步：用代码精细控制（流式事件 + 执行追踪）

CLI 简单但不够灵活。下面用 Python 实现，并加上**流式事件**与**执行追踪**——一个管"实时看"，一个管"事后查"：

```python
# report_generator.py
from dotenv import load_dotenv
load_dotenv()

from core import GLMClient, Tracer
from core.config import ConfigLoader
from core.logging_config import setup_logging

DIM, RESET = "\033[2m", "\033[0m"

def print_event(ev):
    """流式事件：思考暗色实时显示，工具调用单行提示"""
    if ev.type == "reasoning":
        print(f"{DIM}{ev.content}{RESET}", end="", flush=True)
    elif ev.type == "text":
        print(ev.content, end="", flush=True)
    elif ev.type == "tool_call":
        print(f"\n{DIM}· 调用工具 {ev.content['name']}{RESET}", end="", flush=True)

def main():
    setup_logging()

    # 1. 加载配置并构建团队
    loader = ConfigLoader()
    config = loader.load_file("configs/report_generator.yaml")
    llm = GLMClient(model=config.model)
    _, agents, _ = loader.build(config, llm_client=llm)
    team = loader.build_team(config, agents)

    print(f"团队就绪：{team.name}，成员 {[m.agent_id for m in team.members]}\n")

    # 2. 开启执行追踪（事后复盘用）
    Tracer.enable()

    topic = "人工智能在医疗领域的应用现状与前景"
    print(f"研究主题：{topic}\n{'='*60}\n")

    # 3. 执行：最终报告（作家的产出）逐字实时流出
    Tracer.start_trace("研究报告任务")
    report = team.run(topic, stream_callback=lambda s: print(s, end="", flush=True))
    trace = Tracer.end_trace()

    print("\n" + "="*60)
    print(report)

    # 4. 复盘：谁做了什么、多久、多少 token
    print("\n" + "="*60)
    print(trace.format_text())

if __name__ == "__main__":
    main()
```

> 想让**每个成员**的执行过程都实时可见（而不只是最终报告），可以在自定义 Agent 的
> `receive` 或对 `think` 做薄包装时传入 `events_callback=print_event`（见第 2 章 §2.6）；
> `team.run` 的 `stream_callback` 只作用于最终产出方（作家/Leader 汇总）。

## 第 5 步：理解执行追踪

运行上面的代码，`trace.format_text()` 会输出类似这样的时间线：

```
=== Trace: 研究报告任务 ===
总耗时: 28.5s   总 token: 3240   span 数: 9

  think:项目经理          6.1s  total_tokens=210     (拆解任务，结构化输出)
  hierarchical:researcher 3.2s  capability=search    (联网搜索)
  think:研究员            3.2s  total_tokens=380
  hierarchical:analyst    2.8s  capability=analysis  (分析趋势)
  think:分析师            2.8s  total_tokens=295
  hierarchical:writer     4.5s  capability=write     (撰写报告)
  think:作家              4.5s  total_tokens=540
  think:项目经理          7.1s  total_tokens=815     (汇总终稿)
```

从这个追踪你能清楚看到：
- **Leader 第一步花 6.1s 拆解任务**（JSON 模式约束下的子任务规划）
- **研究员联网搜索**用了 web_search 工具（所以耗时长些）
- **作家写报告花 4.5s**（产出最长，token 最多）
- **Leader 最后汇总**耗时最长（要把所有产出整合成连贯报告）
- **总成本 3240 token**——每个 span 的 total_tokens 是本次用量，可直接核算成本

这就是 Trace 的价值——把黑盒的团队协作变成**完全可观测**的过程。

## 第 6 步：断点续跑——长任务的崩溃恢复与分段执行 ⭐

研究报告这类任务动辄几十秒、十几次 LLM 调用。两个真实痛点：**中途崩了全部重来**（重复付费）、**想先看看中间产出再决定继续**。检查点（第 6 章）一次解决：

```python
from core import FileCheckpointStore

team = Team(..., checkpoint_store=FileCheckpointStore(".checkpoints"))

# 场景 A：崩溃恢复——同 run_id 重跑，从断点继续，已执行成员不再重跑
report = team.run(topic, run_id="medical-ai-report")

# 场景 B：分段执行——先跑 1 步看看质量
outcome = team.run_resumable(topic, run_id="medical-ai-report", step_limit=1)
if not outcome.completed:
    print(f"已完成 {outcome.steps_done} 步，中间产出：")
    # ... 检查 SharedContext 的产出 ...
    outcome = team.run_resumable(topic, run_id="medical-ai-report")  # 满意后续跑
print(outcome.result)
```

要点：
- 每完成一个成员/子任务就**原子落盘**（含整个共享黑板），崩溃最多损失进行中的一步
- Hierarchical 续跑会**复用断点里的规划**——Leader 不再花一次 LLM 调用重新拆任务
- 已完成的 run 同 run_id 再执行，直接返回缓存结果（幂等，零 LLM 调用）
- 换了研究主题（任务描述变化），旧检查点自动作废重来

## 第 7 步：并行与成本优化

### 优化 1：并行子任务（压缩耗时）

研究员查资料、分析师读数据如果**互不依赖**，可以并行。YAML 一行开启：

```yaml
team:
  process: hierarchical
  parallel: true    # 子任务按成员分组并行：组间并行、组内串行
```

注意权衡：并行模式下各子任务拿不到彼此的产出（同时进行）。本项目的"研究员 → 分析师"有依赖关系（分析师要读研究员的资料），**不建议**全开并行——但把"研究员 + 另一个独立调研角色"并行是合理的。每步内的多个工具调用（比如研究员同时搜三个关键词）本来就自动并发（第 2 章）。

### 优化 2：控制成本

- 减少 `max_subtasks`（让 Leader 少拆几个子任务）
- 换用 Sequential 流程（固定流水线，比 Hierarchical 少一次"规划"调用）
- 推理模型按需开关：`GLMClient(model="glm-4.7-flash", thinking=False)` 关闭深度思考，普通步骤省 token；只给 Leader 的规划/汇总开 `thinking=True`

```yaml
team:
  process: sequential        # 改为顺序接力
  members: [researcher, analyst, writer]
  # 不需要 leader
```

### 优化 3：让报告更结构化

调整作家的 system_prompt，要求严格的输出格式：

```yaml
- id: writer
  system_prompt: |
    你是报告撰写员。输出必须严格遵循格式：
    # {报告标题}
    ## 背景与概述
    ...
    ## 核心发现
    1. ...
    ## 结论与展望
    ...
```

### 优化 4：加入向量记忆（积累经验）

让团队记住历史报告，下次类似主题能复用（第 4 章）：

```python
from core import VectorMemory, LocalTfidfEmbedder

vm = VectorMemory(embedder=LocalTfidfEmbedder())
vm.add("上次的量子计算报告：重点关注了量子纠错和退相干问题")
agents["leader"].set_vector_memory(vm)
# 现在 Leader 在规划时会"想起"相关的历史经验
```

## 第 8 步：扩展思路

| 扩展方向 | 怎么做 |
|----------|--------|
| **支持文件输入** | 给研究员加 `file_read` 工具，读本地资料（敏感文件默认拒读） |
| **数据支撑** | 给分析师加 `database` 工具，查询真实数据（只读模式防误删） |
| **接入 MCP 生态** | `tool_registry.register_mcp_server(MCPServerConfig(url=...))`，一键挂载任何标准 MCP 服务器的工具（第 3 章） |
| **多轮迭代** | 用 Sequential 流程加一个"审核员"角色，反复打磨 |
| **导出格式** | 报告产出后用 Python 写入 markdown/html 文件 |
| **并发服务化** | asyncio 场景用 `await team.run_resumable(...)` + `agent.think_async`（第 7 章） |
